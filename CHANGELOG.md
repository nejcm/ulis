# Changelog

All notable changes to this project are documented here. The format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); this project follows [SemVer](https://semver.org/).

Releases before this one predate this file. See [GitHub Releases](https://github.com/nejcm/ulis/releases) for their notes.

## [0.8.0] — 2026-08-20

**`ulis install` could delete files it did not write.** Every release up to and including 0.7.0 swept the OpenCode destination directory clean of every top-level entry that was not in the generated set — ignoring `--no-prune` and ignoring the ownership manifest, which exists precisely to decide what ULIS may remove. On Linux and macOS, `--global` pointed that sweep at `~/opencode`, a directory the docs never named (they say `~/.config/opencode`). **If you have ever installed the `opencode` target, check `~/opencode`, `~/.opencode` and your projects' `.opencode/` for anything you put there yourself.** This one has nothing to do with remote sources — a purely local `ulis install` reached it. See **Fixed** below; the destination moves in this release and you have to act on the old one yourself.

0.7.0 introduced remote sources (`--source`/`--preset` accepting a git URL) behind a trust gate meant to stop unreviewed remote code from reaching your machine. That gate had several ways around it, closed in this release. **If you have used a remote `--source` or `--preset` on 0.7.0, treat anything it installed as unreviewed and re-run the install after upgrading.** If you have only ever used local sources, the remote-source items below do not apply to you — the OpenCode data loss above still does.

Re-running the install replaces the managed files, but it cannot undo commands that already ran during a 0.7.0 install, and it does not remove anything written outside ULIS's ownership manifest — there is no `ulis uninstall`; removal only happens via prune against a shrinking generated set. If you installed from a source you do not fully trust, audit what those `npx`/`bunx` commands did as well.

### Security

- **The gate shipped in 0.7.0 was broken in three ways.** It confirmed only _after_ the generated config files were already written to disk, so declining left them installed regardless of the answer. It listed only what a source _declared_ in `skills.yaml`/`extensions.yaml`, not what the generator actually _emitted_ — MCP servers weren't enumerated at all, and a hook that reached the output through another path never appeared in the prompt either. Running with no terminal attached (a script, a CI job) silently declined and exited `0` — indistinguishable from a successful, reviewed run.

  Fixed: the gate now stands in front of every write and lists what the generators actually emit — regenerated in memory from the same inputs the install uses, so the preview cannot drift from what lands — including approval-policy entries that widen what your agent may do without asking (a new entry class in what's shown — see **Changed** below); declining installs nothing at all; and no terminal is a hard failure instead of a silent decline (pass `-y` for scripted/CI runs that have already reviewed the source).

- **A remote source's `.env` was read before the gate ran**, letting it set environment variables that 0.7.0's denylist did not cover — `HOME` and `XDG_CONFIG_HOME` (which is how an attacker reaches `~/.npmrc` indirectly), `USERPROFILE`, `ComSpec`, and `SSH_AUTH_SOCK` — that the very `npx`/`bunx` command you were about to approve would then trust. Fixed: a remote source's `.env` is never read at all, and the denylist that protects a local source's `.env` gained those keys.

- **Cross-run bypass.** `ulis build --preset <url>` followed later by `ulis install --skip-rebuild` installed the remote preset's MCP servers, hooks, and raw config fragments with no prompt at all, because the second run had no way to know the tree it was about to install came from a remote source. Fixed: each platform's provenance record now lives in the output it describes and is written by the same operation. `--skip-rebuild` refuses if any platform it is about to install carries one. See **Behaviour changes** below; this fix is behind two of the three breaking changes in this release.

- **Identity mixup in the TUI.** The interactive installer decided whether a source was "remote" by checking whether its temp directory name started with `ulis-remote-`, rather than asking the resolver that already knew the answer. A local project directory that happened to share that name prefix had its own `.env` silently skipped for the run. Fixed: the TUI now uses the resolver's own answer instead of guessing from a name.

- **Injection in generated output.** A remote source's `mcp.yaml` server name, or an unrecognised key that ULIS carried through verbatim, could break out of its position in generated Codex TOML or YAML output and smuggle in an extra config block — including a `hooks:` block the trust preview never looked for, because it appeared nowhere a source declares hooks. A `security.blockedCommands` pattern containing a `"` could break out of the shell command it was interpolated into. Fixed by quoting/removing the interpolation rather than filtering characters, since a character blocklist would have refused exactly the patterns a security-conscious user writes.

- **The same class, inside the generators themselves — a source's prose could rewrite the config it was embedded in.** Four positions, each reachable from an ordinary agent, rule or policy field:
  - Codex agent files emitted the agent body verbatim between `"""`, so text in the body could close the TOML multi-line string and append live top-level keys. The proof-of-concept set `sandbox_mode = "danger-full-access"` on the generated agent.
  - Cursor and ForgeCode built their frontmatter by string interpolation, so an injected `---` closed the block early and left the generator's own `readonly: true` and `tools` stranded in the body as inert prose. Claude and Cursor rule frontmatter had the same shape: `description:` interpolated raw, path globs hand-quoted with literal quote characters.
  - The security policy's own fields — `blockedCommands`, `restrictedPaths`, `requireApproval`, `prefer`, `avoid`, `excludeFromContext` — went into the generated policy comment block unescaped. `makeComment` prefixes each line with `#` individually, so a newline in a value produced an unprefixed line of live TOML or YAML; and the Markdown block is an HTML comment, so a value carrying `-->` ended it early and everything after read as live instruction text. `--!>` closes an HTML comment too, and escaped the block on all four Markdown platforms.
  - Rule names come straight from on-disk filenames, where a newline is legal, so a remote preset source could forge extra bullets into the victim's live `AGENTS.md` on codex, opencode and forgecode.

  Fixed by building each of these positions as data and serialising once, not by filtering characters: a Codex multi-line escaper that makes the `"""` delimiter unforgeable, one shared `serializeYamlFrontmatter` for every frontmatter generator (hardened for nested values, control characters, lone surrogates, number-like and date-like strings and keys), and escaping — not truncation — of every policy-comment field. Codex, OpenCode and ForgeCode rules need no frontmatter fix: they emit only the body. Cyclic aliases, non-plain frontmatter values and 100-deep nesting are now rejected in the parser with the usual source diagnostic, before any file is written, instead of escaping the generator as a bare message over a half-written output tree.

  Eleven vulnerabilities were proven against the real `analyzeProject` → `generate` pipeline in a hostile-corpus harness before any of them were fixed, each held as a failing test until its fix landed. All eleven are closed; none remain open.

### Changed

- **The ownership manifest is now version 2.** It records the destination's top-level entries, which is what makes the OpenCode root sweep manifest-driven instead of unconditional. A v1 manifest is accepted and migrated, so existing installs keep working — but v1 carries no record of what ULIS owned at the root, so it is read as "sweep nothing". **Your first install after upgrading prunes no top-level entries in the OpenCode destination**, and rewrites the manifest as v2; pruning resumes from the second install onwards. If you expected a stale top-level directory to disappear and it did not, run the install again.
- The TUI's remote-review header no longer reads "These commands come from `<source>` and WILL RUN if you continue" — some listed entries (approval-policy changes, files a host agent reads later) don't run as a command themselves. It now reads "`<source>` contributes the entries below, and they WILL take effect if you continue. Review them first:", followed by a line naming the three ways an entry can matter: it runs during the install, it runs later inside your agent, or it widens what your agent may run without asking.
- The TUI now rejects a review used to start a different action with an explicit error, rather than relying on the settings fingerprint incidentally encoding which action it was generated for.
- The remote command list is now printed under `-y` as well. `-y` used to return before the "Remote Source Commands" block, so it skipped the disclosure and not just the prompt — contradicting `docs/guide/remote-sources.md`, and doing so in CI, which is exactly where the record matters because nobody is watching the terminal. Disclosure and the fingerprint check consume the same rendered plan, so what is shown cannot drift from what runs.

### Added

- CI now regenerates the README's `tui.svg` screenshot on every pull request and fails if it doesn't match the committed file, so it can no longer drift from what the TUI actually renders unnoticed.
- CI runs on pushes to `master` and `develop`, not pull requests only — `develop`, where everything lands, had no coverage at all. It builds the bundle before testing (the test asserting the Node CLI never pulls in OpenTUI returned early when `dist/cli.js` was missing, which in CI it always was, so it had never once executed), and it runs `format:check` and the Node smoke build.
- Every action in the release workflow is pinned to a commit SHA. That job holds `NPM_TOKEN`, so a compromised mutable major tag would have run with the publish token in scope. `id-token: write` is added for npm provenance; `--provenance` itself is not, since it belongs in `scripts/release.ts` and would break a local `bun run release` ungated.

### Fixed

- **A global OpenCode install deleted unrelated files in `$HOME`.** `ulis install --global` on Linux and macOS wrote to `~/opencode` rather than the documented `~/.config/opencode`, then removed every top-level entry there that was not in the current generated set. `--no-prune` did not stop it and the ownership manifest was not consulted, so entries ULIS had never written were removed alongside its own. Four unrelated files and directories were removed in the reproduction. A project install had the same unconditional sweep against `.opencode/`.

  Fixed three ways: the destination is corrected to `~/.config/opencode` (pinned by a literal-path test so the registry cannot drift from the docs again); the root sweep is manifest-driven, removing only entries a previous install recorded as its own and absent from the current generated set; and `--no-prune` holds there like everywhere else.

  **Migration.** Nothing is moved or deleted for you — the fix warns, it does not migrate. After upgrading:
  1. Look in `~/opencode` and `~/.opencode`. A global install that finds a ULIS manifest in either now prints `Legacy OpenCode directory found at <path>. Move its contents to <path> or remove it.`
  2. Move anything of your own out of it, then move any OpenCode config you still want to `~/.config/opencode` and delete the old directory. ULIS will not read it again.
  3. If something is already missing, it is gone — `--backup` defaults to off and there is no undo. Check your backups if you keep them.

  Related, in the same area: `opencode.json` is now skipped during the copy, so a crash mid-install cannot clobber the MCP servers ULIS preserves from it; the same capture/preserve/copy ordering is used by all five installers, with a test asserting every native config filename actually reaches the skip list; and the Claude root config (`.claude.json`) is now backed up and prompted for against the same home-equality check the merger uses, so `--backup` covers it.

- **Install scope followed `--global` instead of the destination.** The destination layout is decided by whether the destination equals your home directory, but external skills were scoped by the flag. Reach a home-layout install without the flag — run `ulis install` from `$HOME`, or point at `--source ~/.ulis` — and skills installed with `--project` into what is really a global destination. All three entry points now derive the scope from the destination. The TUI's remote-command preview shared the bug from the other side: it defaulted to project scope on its own, so it displayed `--project` for an install that would resolve to `-g`, and the trust gate then refused the run for differing from what was reviewed.

- **An interrupt during the write phase raced the writes instead of unwinding them.** Only source and preset resolution were tracked, so during file writes nothing was in flight: a Ctrl-C there ran the cleanups immediately, deleting the temp clone the install was copying _from_, and re-raised the signal mid-copy. Every abort checkpoint inside the write phase was dead code on the CLI path — the copy died on a missing source directory before reaching one. The install call itself is now tracked, on both `install` and `preset install`, so a first interrupt unwinds between platforms and the clone survives the copy in flight. An interrupted install leaves whole platforms rather than half-written ones: a platform's ownership manifest is written only after its install returns, so an aborted platform records nothing and the next install reconciles normally.

- **A platform failure mid-install left the state unstated.** Platforms install in a loop with no rollback, and the first error stopped everything, leaving you to infer from the per-platform headers what had already been written. Failures are now collected per platform, the remaining platforms still install, and `Install summary — installed: [...], failed: [...]` is printed before the first error is rethrown unchanged, with its type, message and nested diagnostics intact. The summary is emitted from a `finally`, so it covers the interrupt path too. An abort is not counted as a platform failure. Full transactionality across platforms remains out of scope.

- **A failed or interrupted install reported success.** On the CLI, a failed external skill or extension produced only a warning: "Installation Complete", exit `0`, with every requested skill having failed. In the TUI, Ctrl-C routed straight to exit, so the process could exit while the installer was still writing the destination and report success for it — as could `q`-cancel followed by quit, and a plainly failed install. Both now report what actually happened, and both exit non-zero. See **Behaviour changes** for what that means for a pipeline. An interrupted TUI install also now says what it managed to do: the summary goes to stderr after the alternate screen is torn down, so it survives on the restored terminal.

- **Generated output was not deterministic.** Directory entries were consumed in raw filesystem order. Node's `readdirSync` sorts via libuv's alphasort; Bun's does not, so entry order followed dirent order, which varies by filesystem (tmpfs by creation order, ext4 htree by name hash) and by checkout order. It surfaced in the rule index bullets in every platform's `AGENTS.md` and in the agent-map key order in `opencode.json` — building two copies of the same source with different creation order produced four differing files. Traversal is now sorted byte-wise in the flat and recursive Markdown walks and in the skill directory walk. The purity test that was supposed to catch this built the same directory twice in one process, so dirent order was identical by construction, and sorted the entries before comparing; it now builds two copies created in opposite order and compares unsorted, for every platform in the registry.

- **`skills.yaml` and `extensions.yaml` were never validated.** `parseProject` read agents, skills, rules, config, MCP and permissions but not these two, so a malformed one built clean — "Validation passed", exit `0` — and failed only at install, as a bare `Error` with no file and no field path. They are the trust gate's execution surface: the record of what a remote source will run was the one part of the config nothing checked. Both now load through the same aggregation and diagnostic reporting as everything else, at every install call site. The TUI's Validate action hand-rolled its own extension loading for the base layer only, so it saw no `skills.yaml` and no preset extensions; it now reports from the parsed project and covers preset layers.

- **Enter was not required to start an install, and what you were consenting to could be off screen.** Three separate defects on the review screens: `handleInstallReviewKey` gated on the toggle keys, so space or `x` — a no-op on most screens — started writing to your config directories; no scroll-into-view existed anywhere in the TUI, so at the supported 50x16 minimum with 24 remote entries the cursor sat on "Start install" with the button itself outside the visible frame; and scrolling the button into view could push the command list it acts on out of frame, so confirming showed zero commands and no warning. Now: only the Enter family starts an install, the plan and command list scroll in their own pane while the warning and action rows sit in a fixed one, and every command row must have been painted contiguously before Enter starts anything — a blocked Enter scrolls to the first unseen command and says so. The acknowledgement is recorded in rendered lines, so a resize clears it rather than letting a widened terminal satisfy a partial traversal.

- **A review's remote state outlived the review.** `navigateBack` cleared neither the command list nor the prepared clone, so a local review could display a previous remote source's URL, its red warning and its commands — a threat notice for something that was not about to happen. The credential-bearing clone stayed in `/tmp` too, along with the temp root holding its git objects and config. Leaving a review now clears the display state and disposes the clone, driven by an explicit intent at the three call sites that leave one rather than inferred from the current screen (inferring it meant a stray keypress mid-install deleted the directory the installer was reading from). The fingerprint and the post-review-edit refusal are unchanged: consent is enforced against the prepared review, not against screen state.

- **An older ULIS overwrote a newer one's preferences.** `applyTuiPreferences` returned silently on a preferences version it did not recognise, the controller seeded from defaults, and the first change wrote v2 over v3 — destroying keys it had no idea existed. A future version now suppresses saving for the whole session and says so. The guard sits on the single persistence method, so every change path is covered.

- **Every termination signal reported success.** A `kill` to the TUI exited `0`: OpenTUI claimed eight signals of its own and its handler is a bare `renderer.destroy()` with no exit, so the renderer came down, the event loop drained, and the process reported a clean run — for a terminated install, with the temp clone still on disk. `kill -QUIT` exited `0` with no cleanup at all. The interrupt guard now owns termination, is created before the renderer so it is first on every signal, and routes into a shutdown that aborts, waits for what is in flight, disposes the clone, writes the summary to stderr and exits `128 + n`. OpenTUI registers no signals now. SIGQUIT joins the guard's set and the Node launcher forwards it; SIGABRT, SIGBUS and SIGPIPE deliberately do not, since running cleanup on a process that is no longer sound is worse than not.

- A full build now replaces removable files, symlinks, FIFOs, and sockets at a generated platform path, so the full build that ULIS's provenance errors tell you to run can actually regenerate the tree.

- A second Ctrl-C while a remote clone was still being aborted used to be ignored, and a cleanup step that itself threw (a locked file on Windows, a flaky network mount) could strand every cleanup still queued behind it and surface as an uncaught exception inside the signal handler. A repeat interrupt now exits regardless, and cleanups run inside a `try`/`catch`.

- **The docs described a tool that did not exist.** `docs/REFERENCE.md` shipped as five empty headings behind nine inbound links, two of them pointing at an anchor that had never existed: its generator still imported `zod-to-json-schema`, which is v3-shaped and emits nothing for Zod v4 constructs. It is ported to `z.toJSONSchema` and now generates 56 field rows over six sections, byte-stable across runs; `zod-to-json-schema` is gone from the dependencies. `docs/index.md`, the first page a visitor sees, carried a hardcoded `v0.0.30` badge (now read from `package.json`), `ulis.yaml` for what is really `config.yaml`, `mcp/` as a directory when it is `mcp.yaml`, flat skill files when skills are directories, and dotted platform names under `generated/`; `CliDemo.vue` on the same page was wrong the same way, including a summary line the CLI never prints. `docs/CLI.md` now documents `.env` loading — precedence, parse rules, post-install cleanup, and why a remote source's `.env` is never read — which had zero mentions across README and docs despite being a security bullet above. `ulis check` is removed from the docs rather than implemented: nothing ever defined it, and `ulis build` already performs the validation it described. And `bun run dev:install`, documented as installing "into global configs", actually resolved its destination to the repo root — which holds this repo's own `.claude/`, `.codex/` and `.cursor/` — with `--yes` and prune on; it now copies `example/` into a fresh temp directory and installs there.

### ⚠ Behaviour changes

1. **A previously-approved `--skip-rebuild` may now refuse.** If you have run `ulis install --preset <url>` (or `--source <url>`) and approved its commands, that install now leaves a provenance marker inside each generated platform it touched. Any _later_ `ulis install --skip-rebuild` against that same generated tree hard-fails with an error naming the recorded source — `-y`/`--yes` does **not** override this. It is deliberate: skipping the rebuild also skips the one thing that lets the gate re-verify what it is about to install.

   **If a pipeline does `install --preset <url>` once and then repeatedly `install --skip-rebuild`:** drop `--skip-rebuild` from the later step — but note this rebuilds from your local source alone, so the remote preset's contributions stop being installed; or keep re-supplying `--preset <url>` so the gate reviews it fresh each time and its contributions are preserved.

2. **Upgrading from 0.7.0: run one full `ulis build` before your first `--skip-rebuild`.** A tree built by 0.7.0 with `--preset <url>` has no provenance record — the feature didn't exist yet — and this release reads "no record" as "purely local," so it will not refuse that tree.

   It must be a _full_ build, and the reason is not the record: it is that a build only regenerates the platforms it targets. A full build overwrites every platform directory with purely local output, so the remote-authored files from 0.7.0 are gone. A narrow `--target codex` build leaves every other platform's 0.7.0 output exactly where it is — checking the provenance record afterwards would show it clean either way, because a clean record and a remote-authored file still sitting on disk are two different things.

   This is a known, deliberate limitation, not a defect. The alternative — refusing every `--skip-rebuild` on any tree with no record at all — would break the common case: everyone who has only ever used local sources and has never touched `--preset <url>`.

3. **`--skip-rebuild` no longer applies when this run resolves a remote source.** `ulis install --preset <url> --skip-rebuild` now rebuilds anyway and logs why: the gate previews what the build produces, so installing a pre-existing `generated/` tree would show you one thing and install another.

4. **Permission lists are base-wins, not additive.** `claude.allow`/`deny`/`ask`, `claude.additionalDirectories` and the two `cursor` allowlists used to be concatenated across every layer, with no dedup and no way to take an entry back — so a preset declaring `allow: ["Bash(*)"]` reached the generated `settings.json` whatever the base source said. That was the one class of field where a preset could widen the base's permissions rather than lose to it, and `CONTEXT.md` already said the base wins. Now: a layer that declares one of these fields replaces the inherited value outright, a layer that omits it leaves the value below untouched, and declaring it empty clears it. Entries repeated within a single layer are deduplicated, first occurrence winning.

   **If you layer presets:** diff your generated `settings.json` (and Cursor's allowlists) after upgrading. Anything you were relying on a preset to add is gone if your base declares the same field — re-declare it in the base, since the base's list is now the whole list.

5. **`skills.yaml` and `extensions.yaml` entries merge by identity instead of concatenating.** Both used to concatenate across layers with no dedup and no override, so a preset's entry reached the install whatever the base declared, and an entry repeated across layers installed twice. Entries now merge on `key ?? name`, the later layer winning, with position taken from the first occurrence — the same rule already applied to agents, skills and rules. `key` is what distinguishes two installs of the same package with different args.

   **If you layer presets:** an entry you expected to run twice now runs once, and a base-layer entry sharing an identity with a preset's now replaces it rather than joining it. There is still no removal mechanism — a base can replace a preset's entry, not delete it.

6. **Exit codes now reflect failure.** Several paths reported success for a run that had not succeeded, and any script branching on the status was misled:
   - `ulis frobnicate` printed help and exited `0`. An unknown command is a user error and now exits `1` on stderr; bare `ulis` with no argv still prints help and exits `0`.
   - `--version` printed the version followed by the entire help text, and `--help` printed the help twice. Both now print only what they were asked for. **If you parse `ulis --version`, it is now one line.**
   - `--target ""` leaked `value.split is not a function`, and `--target ","` exited `0` having generated nothing. Both now fail loudly, across `install`, `build` and `preset install`.
   - A failed external skill or extension exited `0`. It now exits `1` and names what failed in the install summary. **A missing `npx` is a failure now, not a skip** — it used to log "skipping extensions" and succeed. If a runner is genuinely absent in your pipeline, pass `--skip-extensions` or `--skip-external-skills`; those still run nothing, contribute no failures and exit `0`.
   - The TUI exited `0` for a failed, cancelled or signalled install. It now exits non-zero, and `128 + n` on a termination signal.

   Also worth knowing before a pipeline goes red: a repeat install re-runs the entries declared in `skills.yaml`, so a non-idempotent external installer that returns non-zero on a second run now fails the install. That exit code belongs to the `skills` CLI, not to ULIS.
